# PRD: v2.1.2, Category Becomes Subtopic

**Product**: PersonalPaper v2
**Release**: v2.1.2 (a vocabulary release, the second, in the shape of `docs/prds/v2.1.1-topic.md`, which it cites)
**Owner**: Patrick
**Date**: 2026-10-25
**Status**: Approved in principle 2026-10-25. Planned; build pending the owner's go.
**Scope in one line**: the word "category", where it names a section of a topic, is replaced by "subtopic" in the database, the topic definitions, the Worker, the agent and the documents, with no change in behavior.

---

## 1. Summary

Every topic is divided into sections: the general topic's twelve follow the Economist's sections, the climate topic's three are the owner's concerns. The system has called them categories since v2.1. The owner, reading the climate topic's sections on 2026-10-25, reached for "sub-topics" and found "category" too general a word: it names any classification, while these sections are the parts of one topic. "Subtopic" names that relation.

This release makes subtopic the only word for the thing, as v2.1.1 did for topic. It renames two database columns, four definition fields, the Worker's handling of them, the agent's instructions and the documents. It changes nothing a reader sees, because pages show each subtopic's name, never the word, and it changes no URL and no stored assignment: subtopic ids such as `weather-volatility` stay as they are.

## 2. The word

**Subtopic**, closed, in prose and in identifiers alike: `subtopics`, `subtopic`, `subtopic_notes`. Identifiers cannot carry a hyphen, and one word everywhere means one spelling everywhere.

**What a subtopic is, today.** A section within one topic's definition: an id, a name, a weight, an optional `max_stories`, and the scope notes that say what belongs in it. Every story belongs to exactly one subtopic of the topic that surfaced it. A subtopic has no registration of its own, no edition of its own, and no reader can subscribe to it alone.

**What the name allows.** The owner's model is that a topic can be a collection of topics at any level, as in pub/sub (vision section 17). The name subtopic is consistent with that: it says "a topic inside a topic". It does not make it true. A subtopic that is also a registered, subscribable topic is a system change for a later PRD; the vision's concept entry says so, so that the name does not promise what the system does not do.

**Words kept apart.** "Subject" keeps its meaning from v2.1.1, an area of interest, as in the deprioritize list and the vision's deprioritized subjects. "Section" stays the ordinary word for a part of a page, and the edition page's headings are the subtopics' names. The RSS `<category>` element on feed items is the feed format's own term and keeps its name in the feed tool's output (`categories` on each item); after this release it is the only use of the word in the repository's code, and it means feed tags.

**The model, updated.** Nouns: topic, subtopic, edition, story, paper. Verbs: publish, subscribe.

## 4. What does not change

- **Every URL.** Pages, the registry, the JSON reads. Story anchors are story ids and do not change. The one fragment that changes is each section heading's anchor, `#cat-<id>`, which becomes `#subtopic-<id>`; nothing links to it since the table of contents was removed on 2026-10-19, and a stale fragment lands at the top of the page.
- **Subtopic ids and names.** `weather-volatility` is still `weather-volatility`; every stored story and candidate keeps its assignment.
- **Stored editions.** The markdown body's `##` headings are subtopic names, which do not change.
- **Legacy strings in the data.** `surfaced_by` and candidate refs from the retired discovery step carry `discovery:<category-id>`; they are data from 2026-10-17 and stay. The schema comments that describe them say `discovery:<subtopic>`.
- **Behavior.** Nothing the agent decides or the Worker renders differs.

## 5. Decisions

Proposed by the session 2026-10-25 for the owner's review, on the pattern the owner approved for v2.1.1.

**D1. Database: two columns renamed in place.** `stories.category` and `candidates.category` become `subtopic`. No table is renamed and no index includes the column; the four indexes are on topic, date, URL, run, stage and flag. The migration is `hosted/migrations/2026-10-25-subtopic.sql`, two `ALTER TABLE ... RENAME COLUMN` statements, rehearsed on a fresh export of the remote database in plain SQLite and in local D1 before it runs remotely, with row counts compared. `hosted/schema.sql` carries the new names.

**D2. Definition fields: renamed, both topics re-posted, no fallback in the Worker.** `categories` becomes `subtopics`, `category_notes` becomes `subtopic_notes`, `category_scope_notes` becomes `subtopic_scope_notes`, and `coverage.discovery_per_category` becomes `coverage.discovery_per_subtopic`. The prose inside the notes changes with them. The Worker reads only the latest version of a definition, so re-posting both topics through `put-topic` the same minute as the deploy is the whole migration: global-us-news v11 and climate-physical-risk v3, each with a vocabulary-only note. Older versions in `topic_versions` keep the old field names as history; nothing reads their fields. A fallback that accepted both names was considered and rejected as the split vocabulary this release removes; the cost of having none is that between the deploy and the re-post, a matter of seconds, an edition page shows subtopic ids as its headings.

**D3. API and JSON: a clean break.** Story and candidate write bodies use `subtopic` for `category`; the Worker's required-field list changes with it. The reads that return stories and candidates (`archive.json`, `cuts.json`, `flags.json`) return `subtopic`. The agent and the Worker move in one commit, and the routine checks out `main` at every run.

**D4. Agent: renamed in the same commit.** Instructions and editorial standard. The aggregate step's "Categorize" becomes "Assign a subtopic"; the budgets table reads "four per subtopic" and "three per subtopic, or the subtopic's `max_stories`"; the proposals paragraph reads "a subtopic empty for several days running". The cover brief does not use the word. The feed tool is untouched (section 2).

**D5. Canon.** The vision's section 6 gains a **Subtopic** entry: a section of one topic, with its id, name, weight, cap and scope notes; every story belongs to exactly one; not yet a topic in its own right, with the pub/sub allowance in section 17 noted. Its v2.1.1 vocabulary note gains one sentence for this release, and its two uses of "categories" are renamed. The README, the guide, the deploy guide where it applies, and the architecture page are rewritten in place. The v2.1 PRD body stays; one sentence is added to the vocabulary line at the top of its closing amendment.

**D6. Cutover: one commit, deployed between the two daily fires.** Remote export as backup; migration remote; Worker deploy; both definitions re-posted; reads verified; pushed. All within a few minutes, outside the windows of the 05:05 and 17:05 ET fires. Verification is the next scheduled fire, or a manual one as the owner chose for v2.1.1.

## 6. The migration

```sql
-- v2.1.2: category becomes subtopic (docs/prds/v2.1.2-subtopic.md, decision D1).
-- Renames in place; rows do not move. Existing databases apply this once; fresh
-- databases use hosted/schema.sql, which carries the new names.
ALTER TABLE stories RENAME COLUMN category TO subtopic;
ALTER TABLE candidates RENAME COLUMN category TO subtopic;
```

Proof on the local copy before the remote: `pragma_table_info` for both tables names `subtopic`; row counts per table match the export; the edition and cuts pages render from the local dev server with headings and kickers intact.

## 7. Build plan

1. **Storage.** Migration file; `schema.sql` rewritten and diffed against the migrated shape; rehearsal on a fresh export.
2. **Definitions.** Field names and prose in both topic files; seed rebuilt and proven on a fresh database.
3. **Worker.** SQL, validation, rendering, variable names. Local dev server against the migrated copy, with the local registry re-posted with the renamed fields: listing, an edition (headings and Top stories kickers), cuts, archive JSON, every write route.
4. **Agent.** Instructions and editorial standard; the tools exercised against the local Worker with a test run dated 2099-01-01, removed afterward.
5. **Documents.** Vision with the Subtopic entry and the note, guide, README, architecture page, deploy guide's upgrade table, one sentence on the v2.1 PRD.
6. **Cutover** per D6.
7. **Verification and close.** One fire's run records and pages; the drive map and the naming memory updated; the parked climate subtopics proposal resumes.
