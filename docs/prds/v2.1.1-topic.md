## 1. Summary

The thing the agent runs each night has been called a profile since v2.1: a definition with categories, agenda and signal sources, a deprioritize list, weights and a cadence. The owner did not recognize the word as naming that thing; it reads as a person's profile. On 2026-10-23, writing the About page, the owner found that "topic" fit the plain description of the product ("read the topics that are posted here", "follow news about any topic") and decided in principle that one word should serve the public and the system alike, because a split vocabulary signals abstractions that are not thought through.

This release makes that one word the only word. It renames the database tables and columns, the one API route and the JSON fields that carry the old word, the agent's instructions and tools, the definition files' directory, and the documents. It also retires "publication" as a second name for the same thing, which the documents adopted in the week before the word was settled. It changes nothing a reader sees except two words of page copy, and it changes no reader URL.

## 2. The word

**Topic** is the pub/sub noun itself (Kafka, SNS and MQTT all publish to topics), so it makes vision section 17 literal: the agent publishes to a topic, a reader subscribes to topics, the paper is the stack a reader subscribes to. It holds up in every system use: a topic definition and its versions, a topic's sources and cadence, the registry of topics, a run for a topic, the paper stacks topics. The word carries no level, which the owner noted is right: a topic can be a collection of topics, as in pub/sub, and the paper stays outside that recursion, named for the reader.

**The model**: nouns are topic and edition, with story and paper alongside; verbs are publish and subscribe. Candidates set aside on the way: desk, beat, title, charter, pub, publication, edition seed.

**Two senses of "publication".** The repository uses the word two ways. In the ordinary sense, a publisher or outlet ("trusted publications say what is significant", "a trade publication", "publication timestamp"), it is correct English and stays; after this release it is the word's only sense here. In the other sense it names the thing this release calls a topic, adopted in vision section 17 and the publication guide during the week before the word was settled; those uses change. The owner folded this in on 2026-10-25 after a reading of every occurrence: the second sense sits only in files this release already opens, and the release's purpose, one word for the thing, is not met while a contributor's first document is titled with the other word.

**Not in this release**: the cadence block the climate topic wants; this release carries no behavior change so that it is easy to verify.

## 4. What does not change

- **Reader URLs.** Every page is `/<id>`, `/<id>/<date>`, `/<id>/<date>/cuts`, `/<id>/archive`, and the id is the topic's slug. Every shared link keeps working. The registry routes `/registry/index.json`, `/registry/<id>.json` and `/registry/<id>/versions` carry no word and keep their paths.
- **The run id form.** `YYYY-MM-DDTHHMM-<id>`.
- **The topic ids.** `global-us-news` and `climate-physical-risk`.
- **Behavior.** Nothing the agent decides or the Worker renders is different, apart from two words of listing-page copy.

## 5. Decisions

Taken by the owner 2026-10-25 on the session's recommendations.

**D1. Database: rename in place.** `profiles` becomes `topics`, `profile_versions` becomes `topic_versions`, and `profile_id` and `profile_version` become `topic_id` and `topic_version` in every table that carries them. SQLite's `ALTER TABLE ... RENAME TO` and `RENAME COLUMN` rewrite the foreign-key references, unique constraints and index definitions in the other tables, so no rows move and no table is recreated. The three indexes named after the old word are dropped and recreated under new names. The migration is one SQL file at `hosted/migrations/2026-10-25-topic.sql`, applied once to the local database to prove the references survive, then once to the remote. `hosted/schema.sql` is rewritten to the new names so a fresh deployment never sees the old ones. Fallback if D1's SQLite does not rewrite the references: create the new tables, copy, drop the old; a few minutes of data either way. Keeping the physical names under a renamed surface was rejected as the split vocabulary this release exists to remove.

**D2. URLs and JSON: a clean break, no redirects, no aliases.** The only route carrying the word is the authenticated write `POST /api/profiles/<id>`, whose sole client is `agent/tools/pp.mjs` in this repository; it becomes `POST /api/topics/<id>`. The JSON field names in write bodies and in the read endpoints (`archive.json`, `runs.json`, `flags.json`, `direction.json`, `cuts.json`) become `topic_id` and `topic_version`, and the registry index's top-level key becomes `topics`. The routine checks out `main` fresh at every run, so the agent and the Worker always move together, and a compatibility shim would protect no one.

**D3. Definitions move to `hosted/topics/`; seed stays the database seed.** The definition files `global-us-news.json` and `climate-physical-risk.json` move from `hosted/seed/` to `hosted/topics/`. The generator `build-seed.mjs` and its output `seed.sql` stay in `hosted/seed/`, which is what every framework calls a database seed. The owner's phrase "seed sources" then has no system term to collide with; documents say "the topic's sources" or "source list".

**D4. Agent: renamed in the same commit as the Worker.** `agent/instructions.md`, `agent/cover-brief.md`, `agent/editorial-standard.md` and the three tools change together. `pp.mjs profile <id>` becomes `pp.mjs topic <id>`, `put-profile` becomes `put-topic`, `fetch_feeds.mjs` takes a topic id, and the `run-open`, `edition`, `stories` and `candidates` bodies use the new field names. The routine's prompt is outside the repository and the owner edits it by hand on cutover day: "every topic in the registry index".

**D5. Canon: the vision revised in place with a dated note; the v2.1 PRD left as the record.** One word everywhere is the decision, so the vision's occurrences change, and section 6, the concepts, gains a dated note recording the rename and the reason, pointing here. Section 17's "the profile as a publication under rename" becomes current. The v2.1 PRD is closed and historical: one line is added to its closing amendment pointing to this PRD, and its body keeps the old word. The README, the deploy guide, the architecture page and the publication guide are live documents and are rewritten in place.

**D7. "Publication" as the thing's name goes too; the outlet sense stays.** Taken by the owner 2026-10-25 after the analysis above. Documents only: the guide renamed and revised, vision section 17 revised with the same dated note as D5, the climate definition's text at its next version. The outlet sense is untouched, so that after the release "publication" means only a publisher, which is cleaner than today, where the vision uses it for both an entity that boosts relevance and the unit the agent runs. "Publish", "subscribe" and "publisher" stay as the verbs and the agent's role.

**D6. Cutover: one commit, deployed between the two daily fires.** The commit carries the migration, the Worker, the agent, the moved definitions, the regenerated seed and the documents. The cutover runs the migration locally, then remotely, then deploys the Worker in the same minute, then the owner edits the routine's prompt. The reads are verified at once. The 17:05 ET fire is the first write test and its run record is read afterward. Each run lasts about ten minutes, so the hazard of a run that began before the deploy writing old field names to the new Worker is avoided by cutting over outside those two windows.

## 6. The migration

```sql
-- v2.1.1: profile becomes topic. Renames in place; rows do not move.
-- Existing databases apply this once:
--   npx wrangler d1 execute personal-paper --local  --file hosted/migrations/2026-10-25-topic.sql
--   npx wrangler d1 execute personal-paper --remote --file hosted/migrations/2026-10-25-topic.sql
-- Fresh databases use hosted/schema.sql, which carries the new names.
ALTER TABLE profiles RENAME TO topics;
ALTER TABLE profile_versions RENAME TO topic_versions;
ALTER TABLE topic_versions RENAME COLUMN profile_id TO topic_id;
ALTER TABLE runs RENAME COLUMN profile_id TO topic_id;
ALTER TABLE runs RENAME COLUMN profile_version TO topic_version;
ALTER TABLE stories RENAME COLUMN profile_id TO topic_id;
ALTER TABLE editions RENAME COLUMN profile_id TO topic_id;
ALTER TABLE direction RENAME COLUMN profile_id TO topic_id;
ALTER TABLE candidates RENAME COLUMN profile_id TO topic_id;
DROP INDEX IF EXISTS stories_profile_created;
DROP INDEX IF EXISTS stories_profile_url;
DROP INDEX IF EXISTS candidates_flagged;
CREATE INDEX stories_topic_created ON stories (topic_id, created_at DESC);
CREATE INDEX stories_topic_url ON stories (topic_id, url);
CREATE INDEX candidates_flagged ON candidates (topic_id, flagged_at);
```

Proof on the local database before the remote: `PRAGMA foreign_key_list(stories)` names `topics`; `SELECT sql FROM sqlite_master WHERE name = 'editions'` shows `topic_id` in the unique constraint; row counts per table match before and after.

## 7. Build plan

1. **Storage.** Migration file; `schema.sql` rewritten; local migration applied and proven.
2. **Worker.** SQL, variables, the route, JSON keys, the listing copy ("Public topics and their daily editions", "all topics"), CSS classes. Local dev server against the migrated local database: registry, listing, an edition, cuts, archive JSON, a write with the token.
3. **Definitions and seed.** Files moved to `hosted/topics/`; generator repointed; `seed.sql` regenerated; `package.json` scripts if any name the path.
4. **Agent.** Instructions, cover brief, editorial standard, three tools. A dry read of the tools against the local Worker.
5. **Documents.** README, deploy guide with a migration section, architecture page, the guide renamed to `docs/defining-a-topic.md` and revised for both words, vision with its dated note covering both words, one line on the v2.1 PRD.
6. **Cutover** per D6, then the first scheduled fire read.
7. **Follow-through.** Each topic's definition text corrected at its next version (`global-us-news` for "profile", `climate-physical-risk` for "publication"), the seed regenerated with them; the local drive map, the climate project's title and the project-setup wording updated where they describe the live system.
